# D1+G2 投递任务（Task B **proxy**）— 残差强化学习

用**冻结的 D1 运动底座** + **残差策略**训练一个"把物体送进桶里"的投递任务。

> ## ⚠️ 先读这一段：这是什么，不是什么
>
> 这是 **Task B 的训练代理环境（proxy）**，**不是官方 Task B**，本目录的任何数字
> **都不是官方成绩**。
>
> | | 官方 Task B | 本 proxy |
> |---|---|---|
> | 物体数 | 18 个（sugar/mustard/banana 各 6） | **1 个** |
> | 抓取 | 真抓取 | **跳过**（物体运动学固定在"虚拟托盘"上） |
> | 释放 | 靠机器人操作 | **脚本触发**（进圈即放） |
> | 桶半径 | 1.0 m | **2.0 m**（见下文"为什么放大"） |
> | 场地 | 官方场景 | 平地 + 1 个桶 |
> | 成绩 | 官方评测 | **proxy 投递率** |
>
> 承载物体的托盘是**运动学的**，**不给机器人任何负载**。所以本工作验证的是
> **目标导航 + 投递几何**，**不是操作能力**。

## 结果

**训练 run**：`weights/taskb_delivery_residual_399.pt`（400 iteration × 256 并行环境，约 6 分钟）

| 指标 | 训练自报 | **独立验证** |
|---|---|---|
| 投递率 | 91.0%（全程） / **96.2%**（最后 512 局） | **98.5%**（672 局），出厂配置回归 **97.4%**（417 局） |
| 物体最终距桶心 | — | **0.266 m**（成功圈半径 1.00 m） |
| 机器人离桶壁最小间距 | — | **0.756 m**（正数 = 没碰到桶） |
| 撞桶次数 | 16 / 7000+ 局 | 0 |
| 行驶距离 | — | 8.38 m / 局 |

**外推测试**（出生点 7.0–8.5 m，**超出训练的 6.5 m 上限**）：投递率 **64.6%**（1084 局），
主要失败模式是 `too_far`（走出 8 m 边界）。超范围会**退化但不会失控**。

验证方式见下文"验证方法"——**独立验证不依赖环境的奖励代码**，用物体世界坐标自己复算。

## 任务定义

```
                    ┌─ 桶（半径 2.0 m，沿高 1.10 m）
                    │
        出生环      │           机器人出生在距桶心 4.0–6.5 m 的环上，
      ╱  4.0–6.5 m  │           朝向随机（±90°）
     │              │
     │   ●──────────┼──── 朝向目标（要学）
     │  机器人       │
     ╲              │           托盘前伸 2.80 m，把物体送到桶上方
                    │           物体距桶心 ≤ 0.40 m 且仍在前进 → 释放
                    └─          物体原地落下 → 停在 0.40 m 处
```

- **观测**：本体感知 81 维 + 目标 9 维（机器人→桶相对向量、朝向误差 cos/sin、物体相对位置、是否还在携带）
- **动作 18 维**：16 维残差关节增量 **+ 2 维学出来的底座指令**（前进速度、偏航角速度）
- **成功**：物体静止在距桶心 ≤ 1.00 m 且低于桶沿

### 为什么把指令放进动作空间

冻结的底座（`flat_lab.onnx`）**只会按指令走路**。如果让策略只用残差去转向，
就是在跟一个训练好的步态控制器对着干。把 `(vx, ωz)` 作为可学习动作喂给底座，
策略就能用**底座自己已经学会的转向能力**去转——这是这个任务能训出来的关键。

## 三个真实踩过的坑（都靠实测发现）

### 1. 第一版任务**根本不用学**

最早的版本让机器人出生时就**对着桶**。未训练策略投递率 **101/103** ——
直着往前走就掉进圈里了，没有任何导航。

**改法**：出生点铺满整个圆周，**朝向随机 ±90°**。朝向不再对齐，"转身"才成为必须学的动作。

### 2. 几何算错，训练卡在 10%

我一开始把桶的尺寸记成"半径 1.4 m、沿高 0.70 m"。**实际代码是**：

```
outer wall radius = 1.00 × bin_scale = 2.00 m
rim height        = 0.05 × scale + 0.50 × scale = 1.10 m
```

基于错误尺寸做的所有间隙推算都是错的。加上释放时**把机器人的前冲速度一起带给了物体**
（相当于抛出去而不是放下），落点比释放点远 0.2 m，策略必须学到"几乎停在桶心"
才落得准——**投递率死在 10–22%**（`delivery_resolved` 5799 次：放了但没进）。

**改法**：
- 释放时**清零物体水平速度**——托盘把物体**放下**，落点 = 释放点
- 托盘前伸 **2.80 m**：机器人**不可能**靠近桶（`base_link`/髋/大腿是非法接触体，
  撞壁即失败），所以必须让**物体**够到桶心，而不是让机器人过去
- 验证过的间隙：释放时机器人底盘在 **3.20 m**（离壁 0.93 m），物体在 **1.43 m** 高
  （沿上方 0.33 m），落在 **0.40 m** 处

改完：**10% → 91%**。

### 3. 课程把难度悄悄删掉了

`CurriculumManager.compute()` 是**每个有环境重置的 step** 都调用一次，参数是整个
batch，不是"刚结束的那几局"。第一版按调用次数调难度，`heading_noise` 在约 200 **步**
（几 iteration）内就从 π 掉到地板，把"随机朝向"这个核心设计**删掉了**。

**改法**：只统计**真正结束**的局，每累计 512 局才调一次，步长按窗口给。

## 训练曲线怎么读

`results/training_metrics.jsonl` 每行一个 iteration：

| 字段 | 含义 |
|---|---|
| `delivery_rate_total` | 进程内累计投递率 |
| `recent_delivery_rate` | 最近 512 局的投递率（**看这个**，累计值会被早期拖住） |
| `recent_mean_min_object_dist_m` | 物体曾到达的最近距离（**精度的直接指标**） |
| `termination_counts` | 各终止原因累计次数 |
| `heading_noise_rad` / `spawn_max_m` | 课程当前难度 |

**典型形状**：前 ~50 iteration 全 0（随机朝向，找不到桶）→ 突然起量 →
`min_object_dist` 从 2.6 m 降到 0.27 m → 收敛。

## 验证方法

`learner/verify_d1g2_taskb_policy.py` —— **独立于训练奖励**的验收：

- 确定性策略（无探索噪声）跑 N 局，**打乱出生点**
- 用**物体世界坐标**自己算"物体到桶心的最小距离"，与环境的 `delivery_success` 交叉对账
- 单独记录**机器人是否碰到桶**、**行驶距离**、终止原因

⚠️ 这个工具自己抓出了两个 bug，值得记下来：

1. `delivery_success` 必须在 `env.step()` **之前**读——Isaac Lab 在 step 内部就重置了
   已结束的环境，step 之后读到的已经是**下一局**的状态
2. 必须按训练的方式调用 `ResidualState.reset(done)`，否则 5 帧历史带着上一局的
   残差/动作跨局，**验证的就不是训练出来的策略**

修正前它报"0 投递 / 1676 自报成功"；修正后 98.5%，与训练一致。

## 单局多趟投递（✅ 已跑通）

一个 episode 内可以连续完成**多次投递**：一趟投放结算后立刻发放下一个物体，不结束回合。

**实测（独立验证，确定性策略）：**

| 检查 | 结果 |
|---|---|
| 多趟 @ 原生配置，64 环境 | 投递 **1628 / 1667 = 97.7%**，**每局 2.83 次** |
| 多趟复现性，96 环境 | 投递 **2431 / 2482 = 97.9%**，**每局 2.81 次** |
| 单趟出厂配置（回归） | 投递 **846 / 859 = 98.5%**，无回归 |

用的是**原本按单趟训练的权重**（`weights/taskb_delivery_residual_399.pt` 的同类 run）——
策略本身会连续投递，**不需要为多趟重新训练**。

---

### ⚠️ 一个必须先讲的教训：真正的 bug 是记账，不是奖励

在此之前，**四个多趟训练 run 全部报告 0 投递**，我当时的结论是"奖励结构导致策略
悬停刷分"，并据此改了奖励（加 holding cost、门控 heading 等）。**那个结论是错的。**

真实原因是一行记账：

```python
# reset_carried_object() 里
state["deliveries_this_episode"][ids] = 0   # ← 每个“投递周期”都被调用一次
```

`reset_carried_object` **既在每回合重置时调用，也在每次投递周期推进时调用**。
所以每成功投递一次，计数就被清零一次 —— **"每局投递数"这个量永远是 0**。
投放、循环、物理**全都是好的**。

修法：把 per-episode 计数拆到独立的 `reset_episode_counters`，只挂在回合重置事件上。

**教训**：连续四轮调奖励都没动，说明模型（"奖励错"）本身没被检验过。
当时该做的是先验证"投放到底有没有触发"，而不是继续调权重。本轮靠 `DROP_PROBE`
（打印 `DROPPED=n`）才发现投放一直在正常工作。

顺带修掉的另外三个真问题（保留在有开关的代码里）：
1. **释放条件要求"同时"满足** → 改为**分别 latch**（物体进圈 + 机器人前进，谁后满足谁触发）。
   物体多次进圈时机器人正在转向、速度不够，窗口就错过了。
2. **成功高度区间不可达**：`z ≤ 0.5` 缩放后 = 1.00 m，而物体释放时在 **1.43 m**，
   判定在释放瞬间必然为假。改为按桶高比例。
3. 奖励防悬停（holding cost / closing 门控 / 时间代价）——**这些不是修复，是加固**，
   在当前配置下不改变结果。

## 已知限制（诚实清单）

1. **不是官方 Task B**——1 个物体、无抓取、脚本释放，见开头表格
2. **托盘前伸 2.80 m 不真实**。这是"机器人不能靠近桶"这个约束逼出来的：
   `base_link`/髋/大腿是非法接触体，桶壁实心，撞上就判失败。真实机器人应该
   用机械臂够过去——那正是本 proxy **跳过**的抓取/操作能力
3. **桶放大 2 倍**（2.0 m vs 官方 1.0 m），同理
4. **外推会退化**：出生点超过 6.5 m 后投递率降到 64.6%
5. **训练/验证在同一台机器、同一 seed 族**，未做跨种子统计（单 run 结果）
6. `time_out` 占比较高（约 130/420），策略有时会磨蹭到超时
7. 多趟投递已跑通（97.7–97.9%，每局 ~2.8 次）。先前"重训两轮仍为 0"的结论**是错的**，真因是记账 bug 而非奖励，详见上一节
