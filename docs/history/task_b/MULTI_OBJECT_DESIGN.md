# 从一次投递到更高分数：多物体设计的可行性

2026-09-14 晚。本文是**设计**，不是已实现或已验证的东西。

## 计分方式（已核实）

`reward_terms` 里 `objects_in_circle` 的 `reward_per_object = 1.0`。实测 d4 跑完 14114 步后
该项总计仍是 **0.0**，而 `grasped_objects` 在一次接近后就是 **1.0** —— **说明这是一次性计数，
不是每步累加**。

**所以分数 = 投递成功的物体数。** 要加分只能多投一个物体，不能让同一个物体待更久。

## 时间预算

单次「抓取 → 高举 → 转向 → 行驶 → 停靠 → 释放」实测约 **500 s**
（前缀 94 + 转向 ~230 + 行驶 ~185 + 手臂/释放 ~30，来自 d18）。

**1200 s 上限内可做约 2 次。** 第三次会超。

## 需要的改动

现在 `PayloadDeliveryPolicy` **组合**一个 `PayloadRaisePrefix`（它就是一次性子策略）。
要跑第二轮，需要在释放后：

1. **收回手臂、重新闭合手指** —— 新的有界阶段；
2. **从桶边驶离**回到物体区 —— 用公开里程计 + 一个有限的路程/时限预算
   （**不能复用静止模块的预算**，这是 `multi_reach` 已知的坑）；
3. **重建一个全新的 `PayloadRaisePrefix` 实例** —— 冻结前缀本身不用改，
   只是重新实例化，让视觉接近重新找一个物体；
4. 状态机回到 `PREFIX`。

## 已知风险（必须先说清）

- **视觉接近能否找到第二个物体完全未验证。** 冻结的 `first_reach` 从出生点在 RGB-D 里找目标；
  从桶边出发它看到什么、会不会反复锁定已经不在的物体，我**没有任何证据**。
- **第一轮释放后手指是张开的**，重新闭合的时序和「空夹」看门狗会互相干扰。
- **物体 3.9–12.0 m 散布**（seed 42 实测），第二趟的路程可能比第一趟长得多。
- 第二轮抓取时的**接近姿态不同**，载荷与髋关节几何要重新核算。

## 建议的推进顺序

1. **先确保单次投递闭环**（d18 正在测），跑独立审计确认是真投递；
2. 再实现第二轮的「收臂 → 驶离 → 重建前缀」三段，**先做 CPU 检查**；
3. 用一个真实回合跑两轮，**独立审计必须能分别关联两个不同物体**。

**在第一次投递被独立确认为真之前，不启动多物体实现。** 否则是在未验证的地基上加层。
